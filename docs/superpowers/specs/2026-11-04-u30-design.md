# U30 (Umsatzsteuervoranmeldung) in `@kreiseck/finanzonline` — Design

**Stand:** 04.11.2026. Faktengrundlage mit allen Quellen und den Ergebnissen
des Testlaufs vom 03.11.2026:
[docs/research/2026-11-03-finanzonline-inventar.md](../../research/2026-11-03-finanzonline-inventar.md)
(im Folgenden „Inventar", Quellenmarken `[Qn]` von dort).

## 1. Ziel und Warum

Kasseneck-Kundenunternehmen sollen ihre Umsatzsteuervoranmeldung direkt aus
Kasseneck an FinanzOnline übermitteln können. Dieses Paket liefert dafür den
Behördenteil: aus fertigen Kennzahlen ein amtlich korrektes U30-XML bauen,
vorher alles prüfen, was sich prüfen lässt, die Zahllast so rechnen wie
FinanzOnline, über den vorhandenen FileUpload senden und das
Übermittlungsprotokoll aus der DataBox auswerten.

Erster echter Einsatz: die UVA Q3/2026 eines Pilot-Kundenunternehmens
(vierteljährlich, fällig 15.11.2026; das Unternehmen hat einen „Benutzer für
WebService"). Danach zwei Berichtigungen (Q1, Q2).

**Ablauf bis Q3** *(Entscheidung Builder, passend zu den Vorgaben)*: Dieser
Plan endet mit einem grünen PR. Für den Q3-Lauf ist **keine npm-Version
nötig** — er läuft über ein Werkzeug außerhalb des Repos (wie das
Testlauf-Werkzeug vom 03.11.) gegen den gebauten Stand, mit den bekannten
Kennzahlen. Zuerst `T` mit dem Zugang des Pilotunternehmens, dann `P` — beides
nur mit ausdrücklicher Freigabe. Das Schärfen des Protokoll-Parsers am ersten
echten Produktionsprotokoll ist ein eigener kleiner Folgeschritt (0.3.1). npm
erst ganz am Ende.

## 2. Ziele, Nicht-Ziele, Anti-Ziele

**Ziele**
- Eingabe in **Kennzahlen** (wie Formular, XSD und FinanzOnline-Maske), alle
  Beträge als **ganze Cent**.
- **Getrennte Schritte statt einer Black Box**: prüfen, berechnen, XML bauen,
  senden, Protokoll lesen — jeder einzeln aufrufbar, die ersten drei ohne Netz.
- Prüfung vor dem Bauen: Pflichtfelder, Zeitraum, Wertebereiche, Vorzeichen,
  unbekannte Kennzahlen, alle BMF-Prüfregeln [Q10], optional der erwartete
  Steuerbetrag je Satz. **Alle** Fehler auf einmal, jeder mit stabilem Code.
- XML exakt nach dem amtlichen XSD (07/2026 bzw. 01/2022).
- **Standard ist immer der Testmodus `T`.** Echtbetrieb `P` nur über einen
  ausdrücklichen eigenen Schalter.
- Ergebnis der Übermittlung und des Protokolls als klares Objekt.

**Nicht-Ziele**
- Keine Ermittlung der Kennzahlen aus Buchungen (das ist Kasseneck-Logik).
- Kein Warten/Pollen auf das Protokoll im Paket (zustandslos; der Aufrufer
  entscheidet, wann er abholt).
- Keine Zählung, wie oft ein Zeitraum schon übermittelt wurde (zustandslos;
  das führt der Aufrufer).
- Keine anderen Anbringen (U13, SB, …) in diesem Schritt.
- Keine Zeiträume vor 01/2022 (anderes Schema mit KZ 009/010).

**Anti-Ziele** (wäre ein Fehlschlag, auch wenn es „funktioniert")
- Ein Weg, auf dem versehentlich `P` gesendet wird.
- Ein XML, das FinanzOnline formal annimmt, das aber nicht dem XSD entspricht
  (FinanzOnline prüft den Wertebereich selbst nicht, Inventar 8.1).
- Stilles Korrigieren von Eingaben (Runden, Abschneiden, Weglassen von
  Fehlerhaftem).
- Eine Laufzeitabhängigkeit.

## 3. Rahmen (verbindlich)

- Paket `@kreiseck/finanzonline`, Node `>=20.18.0`, TypeScript strict, CJS über
  `tsc`, Tests mit `node:test`, **keine Laufzeitabhängigkeiten**.
- Deutsche öffentliche API, wie im übrigen Repo.
- Upload über das vorhandene `fileupload.ts`; DataBox über `databox.ts`.
- Öffentliches Repo: in Tests, Golden-Dateien und Doku nur Ersatzdaten
  (Melisse Nails e.U. / Livia Lindmayr, Steuernummer 91-123/4565 →
  `911234565`). Keine echten Kennungen.
- Ohne ausdrückliche Freigabe wird **nichts** an FinanzOnline gesendet, auch
  kein Testlauf. Der Integrationstest überspringt sich ohne Zugangsdaten.

## 4. Fachliche Festlegungen (belegt, siehe Inventar)

| Punkt | Festlegung | Beleg |
|---|---|---|
| Schema | Struktur „ab 07/2026"; für Zeiträume vor 07/2026 identisch ohne KZ 124/125 | [Q7], [Q12], Inventar 3.1 |
| Reihenfolge | `xs:sequence` laut XSD, nicht numerisch | [Q7], Inventar 3.2 |
| Wertetypen | `kz` > 0, `kznull` ≥ 0 (000, 070), `kzvorz` mit Vorzeichen (063, 067, 090); max. 9.999.999.999.999,99 | [Q7] |
| Zeitraum | Monat: ZRVON = ZRBIS; Quartal: erster/letzter Monat | [Q29], Testlauf T2 |
| Zeichensatz | innere Deklaration `iso-8859-1`; Freitext nur Zeichen aus ISO-8859-1 | Testlauf T11/T15 |
| Transport | `data` XML-escaped (kein CDATA), Request UTF-8 | [Q4], Testlauf |
| Steuer je Satz | `Math.round`-Logik je Zeile, halbe Cent auf | [Q30] § 204 BAO, [Q31] |
| Zahllast | USt − VSt + KZ 090 (Formel Inventar 3.7) | [Q13] |
| Protokoll | flaches `<XML>`; Zuordnung über `PAKET_NR` im `filebez` `Webservice_U30_<ts>_<PAKET_NR>` | Testlauf 8.1 |
| Berichtigung | vollständige neue U30, kein XML-Feld; ARE dann unzulässig | [Q10], [Q37], E1 |

## 5. API

Alle Beträge in Cent (`number`, ganzzahlig). Alles aus
`@kreiseck/finanzonline` exportiert.

### 5.1 Eingabe

```ts
type Zeitraum = { jahr: number; monat: number } | { jahr: number; quartal: 1 | 2 | 3 | 4 };

type Kennzahl = 'kz000' | 'kz001' | 'kz021' | 'kz011' | … | 'kz090';   // genau die XSD-Kennzahlen
type SatzKennzahl = 'kz022' | 'kz124' | 'kz029' | 'kz006' | 'kz037' | 'kz052' | 'kz007'
                  | 'kz072' | 'kz125' | 'kz073' | 'kz008' | 'kz088';

interface U30Erklaerung {
  steuernummer: string;              // FASTNR, 9 Ziffern ohne Trennzeichen
  zeitraum: Zeitraum;
  kennzahlen: Partial<Record<Kennzahl, number>>;
  vst?: string;                      // Ziffer § 6 Abs. 1 zu KZ 020
  ueberschussVerwenden?: boolean;    // ARE = J
  rechnungskopien?: boolean;         // REPO = J
  kundeninfo?: string;               // ≤ 50 Zeichen, ISO-8859-1
  berichtigung?: boolean;            // nur für die ARE-Regel, geht nicht ins XML
  erwarteteSteuer?: Partial<Record<SatzKennzahl, number>>;  // Kontrolle E2
  satzNr?: number;                   // Standard: Position im Paket (1, 2, …)
}

interface U30Paket {
  paketNr: number;                   // 1…999.999.999, vom Aufrufer (eindeutig halten!)
  uebermittler?: string;             // IDENTIFIKATIONSBEGRIFF; Standard: die gemeinsame
                                     // steuernummer aller Erklärungen
  erklaerungen: U30Erklaerung[];     // 1…9999 (BMF empfiehlt ≤ 50)
  erstellt?: Date;                   // Standard: jetzt; geht als Wiener Zeit ins XML
}
```

Kennzahlen mit Wert `0` werden nicht geschrieben (FinanzOnline wertet ein
fehlendes Element als 0), **außer KZ 000**, das immer geschrieben wird
(Pflichtfeld, `0.00` erlaubt = Nullmeldung). Das ist kein stilles Korrigieren:
0 und „nicht angegeben" sind fachlich gleich. *(Entscheidung Builder.)*

### 5.2 Schritte

```ts
pruefeU30(paket: U30Paket, optionen?: { jetzt?: Date }): U30Fehler[]
berechneU30(kennzahlen: Partial<Record<Kennzahl, number>>): U30Berechnung
baueU30Xml(paket: U30Paket, optionen?: { jetzt?: Date }): string      // wirft U30PruefError
parseU30Protokoll(xml: string | Buffer): U30Protokoll
paketNrAusFilebez(filebez: string): number | undefined

createU30(session: Session, optionen?: { transport?: TransportOptions }): {
  sende(paket: U30Paket, optionen?: { echt?: boolean; jetzt?: Date }): Promise<U30Sendeergebnis>;
  protokolle(args: { von: Date; bis: Date; paketNr?: number }): Promise<U30ProtokollEintrag[]>;
}
```

- `jetzt` (Standard `new Date()`) bestimmt „laufender Monat" und „laufendes
  Jahr" in Wiener Zeit — injizierbar für Tests.
- `sende` prüft immer zuerst; bei Fehlern wirft es `U30PruefError` und geht
  **nicht** ans Netz.
- `sende` wiederholt **nie** automatisch: Es setzt `retries: 0`, egal was im
  `transport` steht, damit keine verdeckte Doppelübermittlung entsteht
  *(Entscheidung Builder)*.
- `echt`: nur der Wert `true` sendet `P`. `undefined`/`false` → `T`. Jeder
  andere Wert (z. B. `'true'`, `1`) → Fehler vor dem Netz.
- `protokolle` listet `erltyp=P` im Fenster, nimmt nur `filebez`
  `Webservice_U30_…` (und bei `paketNr` nur diese), öffnet sie (**markiert als
  gelesen**) und liefert sie ausgewertet. Fenster-Regeln der DataBox gelten
  (max. 31 Tage zurück, max. 7 Tage Spanne).

### 5.3 Ausgaben

```ts
interface U30Fehler {
  code: U30FehlerCode;       // stabil, siehe 6
  nachricht: string;         // deutsch, für Menschen
  erklaerung?: number;       // Index in paket.erklaerungen
  kennzahl?: Kennzahl;
  feld?: string;             // z. B. 'paketNr', 'zeitraum', 'kundeninfo'
}

class U30PruefError extends FonError { readonly fehler: U30Fehler[] }

interface U30Berechnung {
  steuerJeSatz: Array<{ kennzahl: SatzKennzahl; bemessungsgrundlage: number; satzProzent: number; steuer: number }>;
  umsatzsteuer: number;      // Σ Steuer je Satz + 056 + 057 + 048 + 044 + 032
  vorsteuer: number;         // 060+061+083+065+066+082+087+089+064 − 062 + 063 + 067
  sonstigeBerichtigungen: number;   // KZ 090
  ergebnis: number;          // KZ 095: > 0 Zahllast, < 0 Gutschrift
  art: 'zahllast' | 'gutschrift' | 'null';
}

interface U30Sendeergebnis {
  paketNr: number;
  uebermittlung: 'T' | 'P';
  angenommen: boolean;       // rc === 0 — nur „zur Prüfung übernommen", noch nicht eingebracht
  rc: number;
  msg?: string;
  xml: string;               // genau das gesendete XML (zum Speichern)
}

interface U30Protokoll {
  uebermittlung?: 'T' | 'P';                 // aus TEXT „TEST-" / „PRODUKTIONS-"
  ergebnis: 'vollstaendig' | 'teilweise' | 'nicht' | 'unbekannt';
  paketAbgelehnt: boolean;                   // SATZNR INFO_DATEN oder „nicht eingebracht/übernommen"
  paketNr?: number; uebermittler?: string; anzahlErklaerungen?: number;
  datum?: string; uhrzeit?: string;          // wie geliefert
  text?: string;
  saetze: Array<{
    satzNr: number | 'INFO_DATEN';
    fastnr?: string; kundeninfo?: string;
    fehler: string[];
    drucktext?: string;
    druckbetrag?: { roh: string; cent?: number };   // Vorzeichen: Gutschrift negativ
  }>;
  abgelehnteSaetze: number[];                // Sätze mit FEHLTEXT
  unbekannteElemente: string[];              // alles, was der Parser nicht kennt
}

interface U30ProtokollEintrag {
  applkey: string; tsZust: string; filebez: string; paketNr?: number;
  xml: string;               // Roh-XML zum Aufbewahren (Testprotokolle löscht FinanzOnline nach 31 Tagen)
  protokoll: U30Protokoll;
}
```

Dazu `istUebernommen(protokoll, satzNr): boolean | undefined` (`undefined`, wenn
`ergebnis` unbekannt), `paketFehler: string[]` im Protokoll und im
`U30ProtokollEintrag` `protokoll?` plus `fehler?`, falls ein Protokoll unlesbar
ist. Eine Erklärung gilt als übernommen, wenn `!paketAbgelehnt` und ihre `satzNr`
nicht in `abgelehnteSaetze` steht (so beschreibt es das BMF [Q15]; im
Testmodus werden übernommene Sätze nicht aufgeführt, Inventar 8.1).

### 5.4 `createFileUpload` (bestehend)

`uebermittlung` wird optional mit Standard `'test'`. Ungültige Werte werfen
vor dem Netz. Abwärtskompatibel.

## 6. Prüfungen und Fehlercodes

Paket: `PAKETNR_UNGUELTIG`, `ERKLAERUNGEN_ANZAHL`, `UEBERMITTLER_UNGUELTIG`,
`UEBERMITTLER_FEHLT` (kein `uebermittler` und Steuernummern verschieden),
`SATZNR_UNGUELTIG`, `SATZNR_DOPPELT`, `FELD_UNBEKANNT` (unbekanntes Feld in
Paket oder Erklärung), `ERKLAERUNG_DOPPELT` (gleiche
Steuernummer und überlappender Zeitraum im Paket — der Testmodus nimmt das
an, im Echtbetrieb wäre die zweite eine Berichtigung bzw. Ablehnung;
*Entscheidung Builder*).

Erklärung — Form: `STEUERNUMMER_UNGUELTIG` (9 Ziffern, 010000010…989999999),
`STEUERNUMMER_PRUEFZIFFER` (Luhn über alle 9 Stellen wie `@kreiseck/validator`;
an einer echten Steuernummer und FinanzOnline-Annahme bestätigt),
`ZEITRAUM_UNGUELTIG`, `ZEITRAUM_NICHT_UNTERSTUETZT` (< 01/2022),
`ZEITRAUM_ZU_ALT` (Jahr < laufendes Jahr − 5), `ZEITRAUM_NICHT_ABGESCHLOSSEN`
(Ende ≥ laufender Monat, strenge Lesart, Inventar 3.6), `KENNZAHL_UNBEKANNT`,
`BETRAG_KEINE_GANZZAHL`, `BETRAG_NEGATIV`, `BETRAG_ZU_GROSS`,
`VST_UNGUELTIG` (Muster laut XSD), `KUNDENINFO_ZU_LANG`, `KUNDENINFO_ZEICHEN`,
`SCHALTER_UNGUELTIG` (`berichtigung`, `ueberschussVerwenden`,
`rechnungskopien` nicht `true`/`false`).

Prüfung und XML-Bau arbeiten auf einer Momentaufnahme der Eingabe (nur
eigene, aufzählbare Eigenschaften, je einmal gelesen).

Erklärung — BMF-Prüfregeln [Q10], je ein Code:
`KZ000_FEHLT`, `STEUERFREI_UEBER_STEUERBAR`, `SUMME_STEUERPFLICHTIG_UNGLEICH`,
`IGE_OHNE_KZ070`, `KZ071_UEBER_KZ070`, `SUMME_IGE_UNGLEICH`,
`KZ066_OHNE_KZ057`, `KZ066_UEBER_KZ057`, `KZ082_OHNE_KZ048`,
`KZ082_UEBER_KZ048`, `KZ087_OHNE_KZ044`, `KZ087_UEBER_KZ044`,
`KZ089_OHNE_KZ032`, `KZ089_UEBER_KZ032`, `KZ020_OHNE_VST`, `VST_OHNE_KZ020`,
`ARE_BEI_BERICHTIGUNG`, `KZ124_125_ZU_FRUEH`.

Kontrolle E2: `STEUER_WEICHT_AB` (mit erwartet/berechnet in der Nachricht),
`ERWARTETE_STEUER_KEIN_SATZ` (Schlüssel ist keine Satz-Kennzahl).

Nicht prüfbar und darum **nicht** geprüft: „bereits eingebracht",
Umsatzsteuersignal, Monat/Quartal passend zum Unternehmen (nur FinanzOnline
kennt das, Inventar 8.2).

## 7. Tests

- **Golden-XML** je Fall als Datei, byte-genau verglichen (festes `erstellt`):
  Pilot Q1/2026 (Gutschrift 999,14), Q2/2026 (Gutschrift 10,94), Q3/2026
  (Zahllast 2.185,34), Nullmeldung, Monat, 4,9 % ab 07/2026, Umlaut in
  KUNDENINFO, Paket mit zwei Erklärungen.
- **Jedes** in Tests erzeugte XML wird offline gegen das amtliche XSD geprüft
  (`xmllint-wasm`, Dev-Abhängigkeit; die BMF-XSDs liegen mit Quelle unter
  `packages/finanzonline/test/xsd/`).
- **Negativfälle** je Fehlercode, mindestens: fehlende Pflichtfelder, falsche
  Rundung (E2), ungültiger/laufender/zu alter Zeitraum, unbekannte Kennzahl,
  falsches Vorzeichen, zu große Beträge, Kommazahlen statt Cent, Umlaut außerhalb
  ISO-8859-1, alle BMF-Regeln.
- **Randfälle:** Gutschrift, Zahllast, Nullmeldung, Monat und Quartal,
  Berichtigung (mit/ohne ARE), Halber-Cent-Fälle bei 10/13/19/7/4,9 %,
  größte zulässige Beträge (BigInt-Rechnung).
- **Transport mit gemocktem SOAP:** rc 0/−1/−2/−3/−4/−5, SOAP-Fault,
  abgelaufene Session.
- **Protokoll-Parser:** die echten Testprotokolle vom 03.11.2026 (redigiert:
  Ersatz-Steuernummer) — OK, NOK mit FEHLTEXT, zwei Erklärungen; dazu
  konstruierte Produktionsfälle (DRUCKBETRAG in beiden Zahlformaten,
  SATZNR INFO_DATEN), als solche gekennzeichnet.
- **Sicherheitstests zuerst rot:** `sende` ohne Schalter → `T`; `echt: 'true'`
  / `1` → Fehler ohne Netz; nur `echt: true` → `P`; `createFileUpload` ohne
  `uebermittlung` → `T`; ungültiger Wert → Fehler ohne Netz.
- **Integrationstest** (`u30.integration.test.ts`): nur `T`, nur wenn
  `FON_TID`, `FON_BENID`, `FON_PIN`, `FON_HERSTELLER_UID`, `FON_STNR` gesetzt
  sind, sonst übersprungen. Ein Login; bei Login-Fehler sofort Fehlschlag, kein
  zweiter Versuch. Sendet eine Nullmeldung für das letzte abgeschlossene
  Quartal und holt das Protokoll (bis 3 min). Läuft nur auf ausdrückliche
  Freigabe.
- Vor dem PR: `npm run lint`, `npm run format:check`, `npm run build`,
  `npm test` im ganzen Repo grün.

## 10. Offen (wird erst an echten Daten geklärt)

- Aufbau des **Produktionsprotokolls** (DRUCKTEXT/DRUCKBETRAG-Format, FASTNR,
  KUNDENINFO). Der Parser ist tolerant gebaut und sammelt Unbekanntes; nach
  dem ersten echten Q3-Lauf wird er an der echten Antwort geschärft.
- Rundung bei genau halbem Cent auf dem Server (Formular-Logik belegt,
  Server nicht).
- Ob die Berichtigung angenommen wird (Anbieter: ja, eine je Zeitraum).
